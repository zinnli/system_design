# 대용량 파일 업로드 — 5분 답변 (화이트보드용)

> **질문**: "여러 개의 대용량 파일을 업로드하는 UI는 어떻게 설계하며, 실무에서는 어떤 점을 고려해야 하나요?"
>
> [DESIGN-GUIDE.md](DESIGN-GUIDE.md)를 **그려가며 5분 안에 말하는 순서**로 재구성한 문서입니다.
> 각 단계는 `그릴 것` → `말할 것`(그대로 읽어도 되는 문장) 구성입니다.
> 특정 구현을 전제하지 않으며, 이 저장소의 실제 구현까지 보여줘야 할 때는 [README.md](README.md)와
> [보드 이미지](docs/upload-board.png)를 씁니다.

---

## 0. 결론 먼저 (0:00 – 0:30)

**그릴 것** — 보드 맨 위

```text
크기가 아니라 "시간"의 문제
→ 정상 경로보다 중단·재개·부분 실패를 먼저 설계
```

**말할 것**

> "이 문제의 어려움은 파일이 크다는 것보다 전송이 오래 걸린다는 데 있다고 봅니다. 수십 초에서 수십 분 동안 사용자는 파일을 더 추가하고, 취소하고, 페이지를 벗어나고, 그 사이 네트워크가 흔들릴 확률도 누적됩니다. 그래서 정상 흐름보다 중단과 재개, 부분 실패를 먼저 설계합니다. 결정해야 할 것을 다섯 가지로 나눠 설명하겠습니다."

---

## 1. 흐름을 네 구간으로 (0:30 – 1:10)

**그릴 것**

```text
[1] 받기  →  [2] 검증  →  [3] 전송  →  [4] 마무리
 선택/드롭    허용·거부    진행률·재시도    완료/실패/취소 확정
                          ·취소
                            ↑ ①~⑤가 여기
```

**말할 것**

> "먼저 흐름을 받기, 검증, 전송, 마무리 네 구간으로 끊습니다. 대부분의 설계 논의는 전송 구간에 쏠리는데, 실무에서 실제로 많이 새는 곳은 검증과 마무리입니다. 거부된 파일을 어떻게 보여줄지, 10개 중 3개만 성공했을 때 다음 단계로 넘겨도 되는지가 초반에 빠집니다. 전송 구간에서 결정할 것들을 이어서 말씀드리겠습니다."

---

## 2. ① 전송 단위 — 쪼갤지 말지 (1:10 – 2:00)

**그릴 것**

```text
단일 요청     수 MB 이하, 다시 올려도 무방
조각 분할     수백 MB↑, 이어올리기 필요   ← 실패 단위: 파일 → 조각
직접 업로드    서버 대역폭·타임아웃 회피

조각으로 간다면:  조각 크기 · 순번(조립) · 재전송 안전성(멱등성)
                                          └─ 서버와 합의 사항 ★
```

**말할 것**

> "전송 단위부터 정합니다. 조각으로 나누면 실패의 단위가 파일 전체에서 조각 하나로 줄어듭니다. 다만 서버 계약과 상태 관리가 늘어나니 공짜가 아닙니다. 그래서 최대 파일 크기, 실패했을 때 처음부터 다시 올려도 되는지, 서버가 큰 요청 본문을 받는지 순서로 판단합니다.
>
> 조각으로 간다면 조각 크기와 순번, 그리고 **재전송 안전성**을 정해야 합니다. 같은 조각을 두 번 보내도 서버의 결과가 같아야 하는데, 이건 프론트가 정할 수 없는 서버와의 합의 사항입니다. **이 보장이 없으면 뒤에 나올 재시도와 이어올리기 전략 전체가 무너집니다.**"

*(★ 표시에 밑줄 — 3단계에서 다시 화살표로 연결)*

---

## 3. ② 동시성 — 상한은 전체 기준 (2:00 – 2:35)

**그릴 것**

```text
파일 A ┐
파일 B ├─▶ ( 전체 동시 상한 하나 ) ─▶ 네트워크
파일 C ┘        나머지는 대기
```

**말할 것**

> "여러 파일을 동시에 올릴 때, 동시 요청 상한을 파일별로 두면 파일 개수만큼 연결이 늘어나 네트워크를 독점합니다. 전체를 아우르는 상한 하나를 모든 전송이 공유하게 하면 파일 수와 무관하게 사용량이 예측 가능해집니다. 값은 브라우저의 호스트당 연결 제한과 서버가 감당할 동시 요청 수를 함께 보고 설정값으로 빼둡니다.
>
> 이때 대기 중인 전송에도 상태가 필요합니다. '시작 전'과 '전송 중'을 구분하지 않으면 대기열에 걸린 파일이 멈춘 것처럼 보입니다."

---

## 4. ③ 실패 — 숨길 것과 넘길 것 (2:35 – 3:20)

**그릴 것**

```text
1층 자동   일시적 오류 ─ 간격 늘려가며 n회 ─▶ 조용히 통과
2층 노출   소진·권한·용량 ─▶ 사유 + 다음 행동 제시

재시도는 처음부터가 아니다 → 성공한 조각 건너뛰고 남은 것만  ←── ★(멱등성)
```

**말할 것**

> "실패는 두 층으로 나눕니다. 일시적인 네트워크 흔들림은 간격을 늘려가며 몇 번 자동 재시도해 사용자가 모르게 넘어갑니다. 간격 없이 연속으로 재시도하면 이미 불안정한 상황을 악화시킵니다.
>
> 자동 재시도를 소진한 실패나 권한·용량 문제처럼 재시도로 해결되지 않는 건 드러냅니다. 이 경계를 명시하지 않으면 양쪽으로 실패합니다. 너무 숨기면 멈춘 줄 알고 새로고침하고, 너무 드러내면 잠깐의 흔들림마다 에러가 튑니다.
>
> 그리고 재시도는 처음부터가 아니어야 합니다. 성공한 조각을 기억해 남은 것만 이어 올리는데, 이게 가능한 근거가 앞에서 말한 멱등성 보장입니다."

---

## 5. ④ 중단 — 세 가지를 구분 (3:20 – 4:00)

**그릴 것**

```text
① 사용자 취소        → 취소로 표시
② 복구 불가한 실패   → 실패로 표시   (①과 뭉개면 안 됨)
③ 이탈·새로고침      → 경고 + 재개 가능 여부

공통: 남은 요청은 반드시 정리
```

**말할 것**

> "중단은 한 가지가 아닙니다. 사용자가 직접 취소한 것과 오류로 중단된 것을 구분해서 표시해야 합니다. 둘을 같은 상태로 처리하면 사용자는 자기가 취소하지 않았는데 취소된 것처럼 받아들입니다. 페이지 이탈은 별개로, 진행 중이면 경고하고 돌아왔을 때 이어 올릴 수 있는지 결정합니다.
>
> 어느 경우든 진행 중이던 요청은 반드시 정리해야 합니다. 방치하면 대역폭이 낭비되고, 늦게 도착한 응답이 이미 끝난 상태를 덮어써 화면이 어긋납니다."

*(시간 남으면 한 줄)* — "완료와 취소가 겹칠 때는 서버가 이미 완료 처리했다면 성공으로 확정하는 편이 안전합니다. 서버와 클라이언트 상태가 어긋나는 게 더 나쁘니까요."

## 6. ⑤ 상태 소유권 + 마무리 (4:00 – 5:00)

**그릴 것**

```text
UI 컴포넌트   보여주기만
    ↑ 구독
업로드 모듈   상태 · 전송 · 재시도 · 취소

대기 → 전송 중 → 성공
          ├─▶ 실패 ──(재시도)──▶ 대기
          └─▶ 취소
```

**말할 것**

> "마지막은 상태를 어디에 두느냐입니다. 업로드는 화면 하나보다 오래 살아 있습니다. 사용자가 탭을 옮겨도 전송은 계속되어야 하는데, 상태를 화면 컴포넌트 안에 두면 언마운트와 리렌더에 전송 로직이 얽힙니다. 그래서 전송 로직과 상태를 화면 밖 독립 모듈에 두고 UI는 구독만 하게 합니다. 화면 생명주기와 전송 생명주기를 분리할 수 있고, 취소나 동시성 같은 까다로운 로직을 UI 없이 검증할 수 있습니다.
>
> 상태 모델 자체는 단순하게 유지합니다. 대기, 전송 중, 성공, 실패, 취소 정도이고 실패는 재시도로 대기로 돌아옵니다. 검증에서 거부된 파일은 이 모델에 넣지 않고 사유와 함께 따로 전달합니다.
>
> 정리하면, 언제든 끊길 수 있다는 전제로 전송 단위를 정하고, 동시성 상한을 전체 기준으로 두고, 실패를 자동과 노출로 나누고, 중단을 구분해 정리하고, 그 전체를 화면 밖에 두는 설계입니다."

## 시간 관리

| 단계 | 내용 | 누적 |
|---|---|---|
| 0 | 시간의 문제라는 프레이밍 | 0:30 |
| 1 | 흐름 4구간 (2·4번이 새는 곳) | 1:10 |
| 2 | ① 전송 단위 + 멱등성 | 2:00 |
| 3 | ② 전체 동시성 상한 | 2:35 |
| 4 | ③ 실패 2층 + 이어올리기 | 3:20 |
| 5 | ④ 중단 3구분 | 4:00 |
| 6 | ⑤ 상태 소유권 + 마무리 | 5:00 |

**넘칠 때 버리는 순서** — ① 5단계의 "완료·취소 겹침" → ② 3단계의 대기 상태 언급 →
③ 2단계의 직접 업로드 방식 → ④ 1단계 그림(말로만)

**절대 빼면 안 되는 것** — 시간의 문제라는 프레이밍 / 멱등성은 서버 합의 사항 /
동시성 상한은 전체 기준 / 재시도는 처음부터가 아니다 / 상태는 화면 밖.

## 꼬리질문 대비

- **진행률은 어떻게?** — 조각 단위 갱신이 단순하고, 조각이 작으면 충분히 매끄럽습니다.
  바이트 단위는 정확하지만 갱신이 잦고 API가 업로드 방향 진행 이벤트를 지원하는지 확인이
  필요합니다. 부정확한 남은 시간 추정은 없는 것보다 나쁩니다.
- **부분 성공은?** — 기본값으로 봅니다. 파일별 상태를 보여주고 "다음 단계 가능 조건"(전부
  성공? 하나라도?)은 제품 요구사항으로 먼저 정합니다.
- **에러 문구는?** — 파일별로 구체적으로. "업로드 실패"가 아니라 "50MB를 초과했습니다".
- **접근성은?** — 드래그&드롭만으로 끝내지 않고 클릭 선택 경로를 항상 두며, 드롭 영역은
  키보드로도 도달·실행 가능하고 진행 상황은 텍스트로도 읽혀야 합니다.
- **파일이 수백 개면?** — 병목이 전송에서 목록 렌더로 옮겨갑니다. 목록 가상화와 진행률
  갱신 스로틀링이 필요합니다.
- **모바일은?** — 백그라운드 전환 시 중단·지연되고, 셀룰러에서 바로 시작해도 되는지는
  별도 판단입니다.
- **조각 크기·동시성 값의 근거?** — 환경에 따라 조정하는 설정값이라는 선까지가 답입니다.
  숫자 자체를 길게 방어할 필요는 없습니다.
- **구현까지 물어보면** — [README.md](README.md)와 [보드 이미지](docs/upload-board.png)로
  실제 청크 크기·동시성·재시도 횟수와 계층 구조를 보여줍니다.
